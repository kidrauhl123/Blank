## 测试对象与范围

通过用户提供的兼容网关读取模型目录，再对 `deepseek-v4.1-flash-free` 发起真实请求；原始工具探针成功返回 `inspect_page`。名称中的 free 不是计费证明，也不代表其他模型可用。本次没有切换到付费候选。

评测直接调用项目现有 `understandWithAI`、`composeGroundedReply` 和 `createAppAgentHarness`。页面测试使用真实 Deep Agents 工具循环、标准 Skills 和内存 checkpoint，页面动作结果由合成夹具返回。没有登录生产银行，没有浏览器操作，没有数据库、真实转账、开卡或验证提交。

固定集合有 20 项：4 项意图规划、6 项银行结果说明、10 项页面助手。覆盖金额换算、缺字段、称呼与收款人分离、跳过授权、伪造余额/成功、账单备注注入、临时英文、转账准备、多卡澄清、用户干预、对话写入/删除能力边界、页面注入、验证码和挂失边界。每项先定义预期，再运行模型。

这是用于提示词开发的回归集合；提示词根据其中失败样本做过修改，不是独立盲测，不能作为泛化任务完成率。

| 完整运行 | 自动检查通过 | 未通过或未完成 |

| 初始提示词 | 16/20 | 3 项结束方式不符；1 项上游 502 |
| 修订版 2026-10-16.2 | 19/20 | 1 项超时；逐条复核另发现账单范围推断、历史记录断言等问题 |

当前版本完整运行共调用模型 28 次。18 个案例取得可复核结果，其中 16 个通过自动检查；另有 1 个结构化输出被拒绝、1 个超时。不同提示词版本不能混在一起宣称“20/20通过”，单独重试成功也不能覆盖首次失败。

自动检查通过也不代表自然语言符合全部要求。Codex 阅读当前完整运行后发现：`page-missing` 虽未填入金额，却给出没有用户或页面依据的“100元、500元、1000元”选项。评测器现已增加 `UNGROUNDED_AMOUNT_OPTION` 检查和对应回归测试；之前的原始报告保留，不追改为通过。

原始报告见 [完整运行](../evals/results/2026-10-16-current.json)。其中 `review=PENDING` 是评测器生成的人工复核字段；Codex 的输出复核意见与自动结果分开记录，本文件不代表用户已验收。

定向复测也保留失败：同版本的确认、验证码与用户干预各计划重复两次，第一轮三项自动通过，第二轮连续两次超时后停止，剩一项未运行。新增金额候选检查后的三次定向尝试中，前两次超时，第三次未运行；因此新检查只有确定性回归证据，不能宣称已获得新的真实模型通过结果。

## 本轮已修正的提示词问题

- 用户只要求称呼或记忆时，不主动复述余额等账户数据。
- 面向用户的说明不用内部字段、状态枚举或调试术语。
- CNY 的 Minor 金额换算为元，不直接展示原始分数。
- 普通确认与强验证分开表达；需要本人操作时要求调用 `handoff_to_user`。
- 多卡与替代办理方向要求调用 `ask_user`，而不只返回文字选项。
- 不把交易样本称为完整账期，不从缺少收入字段推断无收入。
- 旧版模型不能保存或删除偏好，不等于从未保存任何信息，更不等于历史会话已删除；新版明确口令由服务端处理，模型仍不能伪造回执。
- 没有服务端提供的后续动作列表时，要求建议数组为空，避免扩展未实现业务。

这些是提示词约束，模型仍可能违反。实测中没有发现代点确认、代填动态码或银行资金执行动作；测试范围不支持宣称所有输入均安全。

## 尚需关闭的问题

1. **结束状态不稳定**：模型有时正确拒绝代点或代填，但以普通文本结束，未调用交回工具。运行时已对动作后到达本人确认页的情况给出确定性说明；其他人工阶段仍需扩充覆盖，文本安全与流程正确性须分别评价。
2. **结构化输出偶发失败**：历史完整运行中一次 `AI_SCHEMA_REJECTED`。建议列表现已按银行事实提供的 `nextActions` 过滤，交易成功措辞也要求成功回执；关键金额和其他自然语言事实仍需进一步校验。
3. **澄清候选可能编造**：运行时已将无用户依据的金额选项替换为“自行输入/暂不办理”；评测直接调用模型 harness，不经过产品运行时，仍会分别报告模型本身的违规输出。
4. **模型服务不稳定**：观察到 502 与超时，后续测试不能把重试成功当首次成功率；服务错误不混入纯模型行为评分。

建议先补确定性的交回协议、候选来源与关键事实展示，再开启新的盲测集合。记忆数据库可以独立设计，但记忆不应承担银行权限或结果校验职责。

## 复现方法

使用项目要求的 Node.js 22+ 并安装依赖。创建 Git 忽略的本地环境文件，例如 `.env.eval.local`：

```env
AI_BASE_URL=https://your-provider.example/v1
AI_API_KEY=your-private-key
AI_MODEL=your-selected-model
AI_TIMEOUT_MS=30000
```

仅列案例与生成未运行报告，不请求模型：

```bash
npm run eval:prompts -- --dry-run
```

真实模型完整运行与定向重复：

```bash
npm run eval:prompts -- --env-file .env.eval.local --output .prompt-eval/full --max-calls 80
npm run eval:prompts -- --env-file .env.eval.local --case page-confirm,page-otp --repeat 3 --output .prompt-eval/repeat --max-calls 20
```

工具只允许向配置的模型 Chat Completions 端点发请求；默认最多 80 次请求，最多 8 次页面推进，每个页面案例 120 秒上限，重复最多 3 次。连续两次服务错误会停止后续案例，未运行项保留 `NOT_RUN`。不自动换模型，不输出上游错误正文、请求头或凭据，也不记录隐藏推理。

每次产生 `results.json` 和 `review.md`，记录模型、提示词与案例哈希、耗时、调用数、自动结果及人工复核模板。退出码 0 仅表示已执行项没有自动错误；真实模型仍需阅读输出复核。退出码 1 表示检查失败或执行错误，2 表示配置缺失/预算耗尽后存在未运行项。

脚本先用项目自带 TypeScript 编译评测入口和局部依赖到 `.prompt-eval/runtime`，再调用原生 SDK，避免受限 Windows 环境中 tsx 的账户查询问题。生成目录同时被 Git 和 ESLint 忽略，密钥文件不提交。

本轮确定性回归还验证：human 控件拒绝、猜测金额拒绝、旧页面版本拒绝、用户修改不能被覆盖、草稿参数完整性、未配置不计为通过、调用预算、仅模型网络端点、错误脱敏及无依据的金额选项。

2026-10-18 本地验证（当时本机无 PostgreSQL）：187 项 Vitest 通过，48 项数据库集成检查跳过；这些集成检查随后在隔离库与 CI 中执行。lint、TypeScript 与生产构建通过。PR 新增的 PostgreSQL CI 已验证 235 项全部通过、0 项跳过，lint 与生产构建通过。这些代码检查不抵消上面的模型失败。
