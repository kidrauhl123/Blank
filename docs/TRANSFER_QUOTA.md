# 提交时日累计转账校验

2026-10-11 实现。修复预建多笔黄色草稿绕过日累计 1000 元强验证的问题。

## 执行规则

创建草稿时的风险等级是预判。最终提交由 `commitTransfer` 在 PostgreSQL 事务中重新判定：

1. 固定 READ COMMITTED，取得付款客户的 `FOR NO KEY UPDATE` 锁，所有账户和渠道共享该锁。
2. 锁住银行存储的转账和已有验证挑战，再按账户 UUID 排序锁住付款/收款账户。
3. 等待这些锁完成后，用数据库 `clock_timestamp()` 捕获记账时点。
4. 统计该客户在上海当日 `[00:00, 次日00:00)` 内实际执行成功的转账。失败、取消和待确认草稿不计入。
5. 累计加本笔大于 100000 分时要求 MFA。已有红色操作不降级。
6. 首次从黄色升级时，保存 RED/MFA、新挑战、策略与审计，正常结束事务并返回 AUTH_REQUIRED；不记账。即使请求附有验证码，也必须先展示升级详情再由用户重新提交。
7. 后续验证通过才能执行。已成功操作的重复提交返回原回执，不重复扣款。

统计时点、`transfers.executed_at`、账本 `posted_at` 和两侧交易明细时间相同，避免事务在锁上等待跨日后仍按开始时间累计。

使用客户 NO KEY UPDATE 而非 FOR UPDATE，是为了与收款审计/交易外键的 KEY SHARE 锁兼容。双向互转只锁各自付款客户，再按相同账户顺序取得资金锁。

## 渠道与界面

- 两个 APP 提交入口返回 HTTP 409、AUTH_REQUIRED 和强验证信息，在恢复 Agent 之前结束。
- APP 再从银行查询该操作，将黄色确认页更新为红色；清空旧动态码，用户重新确认。刷新失败则阻止继续提交，不能沿用黄色页面。
- QQ / 企微黄色按钮在执行时被升级，返回 MFA_REQUIRED 与银行授权链接，不恢复任务为成功。
- 与操作关联的持久化任务风险和运行记录更新为 RED/MFA，继续保持等待授权。
- 缺少验证码不会新增挑战或增加认证失败次数；错误验证码仍采用原单挑战计数，过期或锁定不自动刷新。

## 验证与复现

使用新的本机临时 PostgreSQL 集群及 bankpilot_test 角色，按名称顺序应用全部迁移，包括 012 的日累计查询部分索引。不要将测试连接到线上数据库。

```bash
BANKPILOT_DB_TESTS=1 \
DATABASE_URL=postgresql://bankpilot_test@127.0.0.1:54189/bankpilot_quota_test \
PASSWORD_PEPPER=test-only \
npm test -- --no-file-parallelism
```

银行核心新增 12 项数据库回归：预建两笔 600 元、首次夹带合法码仍暂停、升级后真实 TOTP 再提交、不同账户并发、1000 元及多一分钱、同操作并发、双向互转、余额不足、过账失败回滚、上海边界/不同数据库时区、锁等待后的记账时间、已红色跨日、挑战过期、IM 任务保持等待及跨客户拒绝。相关场景合并在单项用例中验证。

QQ/企微和两个 APP 接口另有调用边界单元测试。Chrome 新增两项：模拟响应验证黄色切红色后重新输入动态码；真实 API/数据库预建两笔 600 元并从 APP 确认第二笔，只有第一笔扣款，第二笔显示红色及验证要求。

全部套件包含 69 项 Vitest 和 17 项 Chrome 检查；浏览器中的真实银行 API 用例运行于隔离数据库。模型接口替身用例不计为真实模型完成率。

## 已知边界

本实现统计已成功金额，不预占草稿额度：客户级提交锁确保尚未执行的并发草稿必须依次重算，不能绕过累计。若未来接入异步外部清算，须增加处理中额度预留/释放机制。

本次不修复 TOTP 时间步重放、参数指纹校验、黄色草稿有效期、跨草稿失败熔断、可信设备画像、模型事实回复或共享演示身份认证。这些仍是下一批安全工作，不能将本修复描述为完整的交易授权方案。
