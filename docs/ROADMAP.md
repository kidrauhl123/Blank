# BankPilot 整体开发与参赛计划

更新日期：2026-10-09。以本仓库代码审查与赛题原文为依据。
本文是待执行计划，不是完成声明。提交/答辩日期及团队人数尚未确认，因此先确定阶段顺序和验收条件，不虚构日历安排。

## 1. 产品与技术选择

作品定位：银行自营的多渠道 AI 智能体。用户描述需求，系统理解、澄清并规划银行任务；权限、验证与资金执行由银行核心决定。

确定采用：

- 银行 APP 为主入口，官方 QQ、企业微信为辅助渠道。
- 通用 Agent 能力复用成熟 SDK，不自行实现调用循环、上下文压缩或 Skills 加载。当前 APP 可见页面原型采用 Deep Agents SDK，现有业务工作流采用 LangGraph；PostgreSQL 保存任务、授权与 checkpoint。Codex app-server、Claude Agent SDK 均为可评估的替代基座，不能把框架选择等同于自研成果。
- 保留现有 Next.js、银行核心、整数金额、双分录、账户行锁、会话和 outbox。
- 银行工具固定注册并校验参数，模型不获得 Shell、SQL、任意网络或资金直接提交能力。
- 关闭并移除对外 MCP、通用 REST 令牌接入及开发者中心，银行内部业务服务与官方渠道 API 保留。这是下一阶段架构收敛工作，当前代码仍存在这些外部接口。
- 不恢复第二套托管 Agent，不为证明自研而重写通用模型 SDK。
- 开源组件、团队代码和模拟服务在材料中明确归属。

计划覆盖全部六类业务；前三类（转账、账单、卡片）先完成独立闭环，再增加理财、订阅和跨场景服务。

不做：真实银行清算、真实资金接入、自建大模型、开放任意第三方 Agent、假人脸认证和不可验证的“全安全”承诺。

## 2. 当前基线与缺口

已保留的基础：独立 Bank Core，PostgreSQL 事务及有序账户行锁，双分录，银行登录会话，TOTP，LangGraph 授权中断/恢复，QQ/企微官方 Worker，入站事件去重与 outbox。

运行基线：移除旧运行时后，本地 21 项单元测试通过，8 项数据库集成测试默认跳过；lint、TypeScript 与生产构建通过。旧环境清理迁移尚需在部署目标实际执行并核实。不能将这些检查等同于全场景、安全或真实模型验收。

独立原型分支 `feat/visible-app-agent` 增加 APP 主页面与业务弹窗的悬浮接管、结构化选择题、干预暂停和重新观察后继续。真实 SDK / 数据库与浏览器测试使用确定性模型传输或 API 测试替身，未完成真实模型质量验收，也未修复下述银行核心缺陷。详细复现与能力边界见 [VISIBLE_APP_AGENT.md](VISIBLE_APP_AGENT.md)。

审查发现的明确问题：

1. 风险仅在创建草稿时判定；先创建两笔 600 元黄色草稿再提交，可累计 1200 元而不要求 MFA。
2. 已启用 TOTP 可仅凭登录密码换绑；动态码没有消费时间步控制，挑战失败没有形成跨草稿熔断。
3. 授权指纹只写不比对，黄色草稿缺少有效期；设备与行为风险输入尚未形成真实链路。
4. 模型可返回与 BANK_FACTS 矛盾的余额或成功状态；当前事实落地主要依靠提示词。
5. 模型 steps 被保存，但实际执行仍由固定意图分支决定；不是通用 DAG 调度。
6. 不同入口账单范围、日期解释与能力不一致，异常交易缺少实际生成逻辑，部分业务数据为空。
7. 文档中存在超过实际代码能力的描述，需要同步修正。

相关位置：src/lib/bank-core.ts、auth.ts、ai.ts、agent.ts、agent-runtime.ts、policy.ts、bank-statements.ts。
修复前，不新增其他资金写操作。

## 3. 阶段与验收

### M0：完成架构收敛及旧环境退役

工作：

- 提交、推送、部署已完成的运行时删除改动。
- 备份旧数据库、配置和代码；执行 009 清理迁移；撤销旧令牌，移除旧容器与会话数据卷。
- 删除对外 MCP、外部 Agent 开发者页面、用户令牌签发/管理与相关开放平台宣传。
- APP / QQ / 企微均进入同一 LangGraph Runtime，工具服务只接受银行验证后的身份上下文。
- 审计历史与银行交易记录保留；旧渠道绑定不静默迁移。

验收：

- 线上 health 显示数据库连通且 LangGraph ready；前端仅一个助手入口。
- 旧运行时接口返回 404，专用表和容器不存在，旧令牌不能再访问。
- 对外 MCP / 令牌入口删除后，路由与部署配置均无残留。
- 登出用户不能查询账户，两个已登录用户的数据视图相互隔离。
- APP 和已配置的官方 IM 各完成一次查询、黄色确认、红色回 APP 的实测。
- 本阶段不声称修复了 M1 的银行核心问题。

### M1：安全与资金正确性

工作：

- 建立中央 Operation Registry：工具、参数 Schema、基础等级、可升级条件、确认策略、可补偿性、审计字段统一定义，未知操作拒绝。
- 在资金提交事务内以用户为粒度锁定当日额度记录并重算；APP 与 IM、不同账户共享额度，日界线固定 Asia/Shanghai。
- 定义已成功与已占用额度，处理失败/取消释放；执行前风险升级必须暂停并重新验证。
- 授权绑定客户、操作、收款对象、金额、币种、参数版本、期限；参数变化导致旧授权无效。确认页面显示版本，避免内容变更后沿用旧点击。
- 完善 TOTP 初次绑定、换绑与恢复：换绑校验原第二因素，新密钥验证前旧密钥继续有效；消费时间步原子更新，禁止动态码重放。
- 失败计数上升到客户/设备/渠道维度，明确冷却、人工恢复和审计；网络故障与认证失败分开统计。
- 金额、对象和操作状态使用银行事实卡片及确定性模板。模型解释使用事实引用，渲染前核验，不接受“没过账却说已成功”。
- 分类、商户、备注和工具返回中的不可信文本标记来源并按数据处理；模型不提供身份或权限上下文。
- 收紧银行会话写接口的同源校验，内部渠道使用独立认证边界。
- 建立 CI 独立 PostgreSQL 测试环境：数据库集成用例必须实际运行，不以 skip 作为发布通过。

权限表按赛题实现：

| 等级 | 自动化边界 |
| --- | --- |
| 绿色 | 余额、交易、账单、理财收益等纯查询 |
| 黄色 | 日累计不超过 1000 元的转账、虚拟卡、订阅查询/取消等，明确确认后执行 |
| 红色 | 日累计超过 1000 元、改密、挂失/解挂、理财申购，校验真实第二因素后执行 |

卡片一般交易限制/解锁、预算预留等操作在 Registry 单独定义；风险信号只能升级，模型不能降级。缺少已验证设备信息时不写死 trustedDevice=true。

验收：

- 先创建两笔 600 元，再顺序/并发确认：第二笔必须升级强验证或暂停；未验证前不得扣款。
- 跨账户、跨 APP/IM 拆单采用同一累计口径；23:59/00:00 边界有真实数据库测试。
- 重复确认只产生一笔账本交易；余额不足、双向并发、超时重试不破坏账本。
- 旧授权对修改后的金额/收款人无效；过期草稿拒绝执行；跨客户操作拒绝。
- 同一动态码不能授权多次；仅掌握密码无法替换已启用因子；新建草稿不能重置账户失败计数。
- 模型输出“余额 999 元/已经转账”，而银行事实为余额 1 元/未执行时，界面只显示银行事实。
- 故意损坏或失败的事务不能残留半笔资金变动。
- 验收样本全部通过后，再增加其他资金写能力。

### M2：任务 DAG 真正参与执行

工作：

- 意图契约从单 intent 扩展为有类型的任务节点、依赖边、参数及事实引用。
- 计划校验节点白名单、环、资源归属、依赖引用、节点数量与资金参数来源；缺信息先澄清。
- LangGraph 驱动节点状态和调度，不再把 steps 只作为展示文本。
- 查询节点可自动推进；写节点先生成银行草稿，再 interrupt 等待对应确认/强验证。
- checkpoint 保存计划版本、节点输入输出、银行 operation_id 和恢复位置；节点领取与外部副作用使用幂等键。
- 中断、取消、超时及人工接管有明确状态。已过账转账不自动“撤销”；可回退操作使用登记的补偿，不能补偿时转人工。
- 决策日志记录意图、计划、规则、事实、授权及结果，不依赖模型隐藏推理文本。
- 设定最大节点数、模型调用次数、超时与预算；越界时停止并展示已完成/未完成部分。

验收：

- “查上月餐饮消费，再按金额生成 AA”能以账单结果驱动后续节点。
- “给张伟转点钱”只澄清金额，同名收款人只澄清对象，不猜测。
- 服务在等待确认时重启，恢复原草稿；在过账后、回执前重启，不再次扣款。
- 用户取消、修改金额、转人工时，不执行旧计划的后续写节点。
- 查询节点失败后，依赖它的金额计算与写操作不会继续。
- UI 可查看计划和每个节点状态，最终结果由实际完成节点构成。

### M3：转账、账单、卡片三个完整闭环

转账：

- 姓名、手机号与备注；同名澄清，付款账户选择，连续对话补充参数。
- AA 分摊用整数分，尾差规则明确；邀请、参与者确认付款、进度及撤销都有实际状态。
- 定时转账保存时区、周期、截止时间和授权条件；到期执行重新判定风险，升级后通知用户验证。
- 备注参与参数展示及授权绑定，模型不能擅自填入事实性用途。

账单：

- APP / Agent / IM 调用统一账单服务；支持具体年月、月度、年度与比较。
- 基于实际流水实现分类、异常检测及重复扣款/订阅候选识别，展示命中依据与覆盖范围。
- 全年报告不能用最近 50 笔替代；历史不足明确显示覆盖不足。
- 异常提示是风险提示，不宣称确认欺诈。

卡片：

- 指定卡片与多卡澄清；虚拟卡申请、额度设置、交易限制、解锁、挂失/解挂。
- 改密入口纳入红色策略，不让模型、日志或普通聊天保存密码明文。
- 状态变化影响实际交易许可，按钮和后台不能分别维护不同状态。

验收：每类都有正常、取消、歧义、越权、认证失败、重试样本；真实模型驱动至少一条从需求到银行结果的完整路径。

### M4：其余三场景与跨场景调度

理财：

- 比赛银行提供明确标注的模拟产品目录，具有风险、期限、流动性、最低金额和来源说明。
- 风险问卷、适当性约束、产品对比、申购、赎回及状态查询形成闭环。
- 模型不能编造收益或产品事实；申购按红色操作处理，到账状态由模拟银行服务返回。

订阅/代扣：

- 周期流水识别候选，用户核对后建立订阅记录；展示金额、周期与续费提醒。
- 取消商户订阅与银行阻断代扣分别实现、分别回执；没有商户确认不得宣称合同已解除。
- 取消、恢复、重复请求、扣费到期竞争使用明确状态。

跨场景：

- 生日任务包括日期澄清、当月预算预留、提前两天鲜花/蛋糕订单和提醒。
- 使用持久化调度器及模拟商户服务；订单、预算和账本有可查询状态。
- 自动执行仅限用户预先确认的参数、预算与期限；到期重新判定，升级则等待强验证。
- 实际调度和演示时间推进分开；推进必须按到期时间筛选，不能执行所有 scheduled 项。
- 重启、时区、周期任务、重复 tick、商户失败及取消都有幂等与补偿路径。

验收：模拟时钟推进到执行日前不扣款，到期只执行一次；商户失败释放或说明保留的预算；改生日/取消任务不能留下旧订单继续执行。

### M5：评测、演示与作品材料

评测：

- 合成、独立的测试数据库和模拟商户，不污染现有用户账户。
- 可复现数据集：正常表达、省略上下文、歧义、复合任务、提示注入、伪造工具结果、重放与并发。
- 真实模型评测与确定性银行测试分开：记录模型版本、提示版本、运行日期、样本数量和失败样本。
- 金额与权限错误按安全失败处理，不能以总体意图准确率抵消。
- 记录任务完成率、澄清质量、错误执行数、授权绕过数、重复过账数、响应时间和模型调用成本；没有实际运行的指标不填数字。
- 集成测试覆盖部署升级：旧表存在/新安装、令牌撤销、审计保留、服务重启与 checkpoint 恢复。

演示：

- 五分钟内展示一个核心任务、一条依赖前序结果的跨场景 DAG、一条安全攻击被拒绝、一次中断恢复。
- 首选演示：两笔 600 元先建草稿再确认，第二笔升级红色；它直接证明我们修复了公开项目也存在的缺陷。
- 辅助演示：模型编造成功被拒；生日任务按时间执行；多卡或同名歧义只追问一次关键字段。
- 不用测试条数、工具数量或动画规划列表代替实际业务结果。

资料：

- 作品名称与 200 字以内简介。
- 架构图、算法、权限/安全设计、已知风险与自评。
- 10 分钟以内答辩 PPT、5 分钟以内演示视频。
- README、仓库、部署说明、数据准备与测试复现方法。
- 开源依赖与自研贡献对照表。

最终验收：六场景至少各一条完整成功路径，核心安全矩阵全部通过；文档与演示对应实际提交版本，没有“模拟认证当真实认证”“计划生成当任务完成”等表述。

## 4. 具体实施顺序

1. 完成旧运行时上线退役；随后关闭对外 MCP/开发者入口。
2. 修额度提交重算、授权绑定/TOTP 生命周期、跨草稿熔断、事实回复。
3. 让 DAG 进入真实调度，完成持久化中断、恢复和幂等。
4. 完成转账/AA/定时、统一账单/异常检测、多卡管理。
5. 接理财、订阅和生日调度闭环。
6. 固定评测版本，实测、修失败样本、制作材料并冻结提交版本。

每阶段按上述验收放行；先修执行安全，再拓展业务。后续给出截止日期后，将这些节点转换为具体日历与人员分工。

## 5. 自研贡献的答辩表达

通用依赖：Next.js / React、LangGraph、PostgreSQL、模型服务、腾讯官方 SDK。

团队应完成并用代码与测试证明：

- 银行操作契约与中央权限策略。
- 执行事务中的额度判定及绑定具体操作的授权。
- 持久化任务 DAG、人工授权恢复、重试幂等与受限补偿。
- 银行事实校验与可信回执。
- APP 与官方 IM 一致的身份、策略和审计链路。
- 六场景模拟银行服务与对抗评测。

这些成果完成前，材料使用“计划/待实现”；完成后标记对应代码、测试和演示证据。
